# 支持更多游戏类型：方案对比

## 背景

`PlayableAgent` 现在只能产出一种互动形式——翻牌配对（Memory 游戏）。这个机制不是这个项目自己设计的，是 M3 阶段照搬 Python 参考实现（`ads-gen-agent-main/build_playable.py` + `templates/playable/`）搬过来的；参考实现自己的设计文档（`docs/specs/2026-07-17-playable-html5-ad.md`）也明确说这只是"第一版模板"，长期方向是支持更多游戏类型。现在不管广告实际是什么类型的游戏（三消、找不同、拼豆……），`PlayableConfig`（`title`/`ctaUrl`/`tilePrompts`）和 `game.html` 模板都只会产出翻牌配对，只有卡面图片内容会变。

如果要真的支持"游戏类型跟广告实际玩法一致"，有三条可选路径，彼此不是互斥关系。本文档对比这三条路径。

## 方案对比

### 方案 A：多模板 + 确定性选型

**做法**：像 `game.html`（翻牌配对）一样，再建几个独立、自包含的 H5 模板（比如三消一个、找不同一个、拼豆一个），每个模板的交互逻辑是人写死、测试过的固定代码。加一个"选模板"的判断步骤——可以是简单的关键词/枚举映射（`ad.game.genre` 命中"三消"就选三消模板，命中不了就落回翻牌配对当兜底），也可以让 DirectorAgent 或 PlayableAgent 自己的生成步骤多输出一个 `gameTemplate` 字段。`PlayableAgent.assemble()` 按选中的模板类型分支，往对应模板里注入不同形状的配置——翻牌配对要图集，三消要棋子图集+连消规则参数，找不同要两张图+差异点坐标，拼豆要色块网格。**LLM 全程只填模板需要的结构化内容，不碰交互逻辑本身**。

| | 说明 |
|---|---|
| 优点 | 游戏类型和广告实际玩法能对上；复用现有"LLM 填内容、代码管交互"的分工，风险量级和现在一致；每个模板一旦写好、测过，之后所有广告复用同一份代码，出问题"改一次全体受益" |
| 缺点/成本 | 每加一种类型是一次实打实的工程投入——要有人真的把那个玩法的交互逻辑写出来、测试通过，工作量和加一个新 Agent 差不多，不是改提示词就能生效；选模板这一步如果做成关键词映射，覆盖不到的玩法只能落回翻牌配对当兜底，不是真的什么类型都支持 |
| 适用场景 | 业务上能明确圈出几种高频、值得投入的玩法（比如已经有真实三消广告案例），愿意为它们单独投入工程资源 |

### 方案 B：LLM 现场生成游戏代码

**做法**：不建模板，每次直接让 LLM 根据广告描述的玩法现场写一份 `game.html`（含交互逻辑的 JS），理论上什么类型都能"生成"。

| | 说明 |
|---|---|
| 优点 | 理论覆盖面最广，不需要预先决定支持哪些类型 |
| 缺点 | 四条，详见上一轮讨论：①**安全**——这段代码要在真实用户浏览器里被解释执行，不是内部审阅用的数据，LLM 输出=可执行代码和 LLM 输出=数据是完全不同量级的风险；②**正确性没法验证**——游戏逻辑的 bug 往往要真的操作、触发特定交互序列才会暴露，不像图片/文案一眼能看出对不对，而且每次生成都是全新的、没被测过的软件；③**和这个项目一贯的分工原则不一致**——LLM 判断"质"、代码管"构"，游戏交互逻辑属于"构"的范畴；④**出问题没法"修一次全体受益"**——每条广告的游戏代码都是独立生成的孤立个体，不像固定模板那样一处修复全局生效 |
| 结论 | **不推荐**，风险和现有验证方法论的覆盖能力不匹配，不是"值不值得投入"的问题，是"现在这套靠人工确认+模型预筛把关的方法论，管不住动态生成的可执行代码"这个结构性问题 |

### 方案 C：外部 H5 包模式（bring your own real game）

**做法**：完全不生成，直接允许广告方提供一个真实存在、已经做好的 H5 试玩包（游戏公司常见的"playable ad"格式），系统原样把这个包拷进游戏包的 `game/` 目录，跳过 LLM 生成配置、跳过素材生成/拷贝这些步骤。这是 Python 参考实现原本就有的能力（`build_playable.py --game-dir ./h5/`），这次探索发现**容器层的地基其实已经在这个项目里了**——`data/templates/playable/container.html` 已经原样搬了"iframe + `postMessage`（`game_ready`/`game_complete`）+ 超时兜底（`fallback_cta_after_s`）+ `external_game` 标记"这一整套松耦合协议，只是 `PlayableAgent` 现在把 `external_game` 写死成 `false`，从来没有一条输入路径能让它变成 `true`。

| | 说明 |
|---|---|
| 优点 | 游戏是广告方真实提供的，不是 AI 生成/拼凑出来的，玩法和视觉 100% 准确；工程成本低——容器层协议已经现成，只需要加一个"上传真实 H5 包"的输入方式 + `ab_ad` 记一下路径 + `assemble()` 加一个"有就直接拷贝，跳过生成"的分支；不需要为每种玩法单独写代码，容器不关心 `game/` 里到底是什么类型的游戏 |
| 缺点/前提条件 | **业务前提，不是技术能不能做的问题**——依赖广告方真的愿意/能够提供这样一个 H5 试玩包，如果广告方只有视频素材、没有现成的可玩 H5 版本，这条路径就用不上；容器和游戏之间的 `postMessage` 协议是可选的，如果外部包不实现它，"游戏是否真的通关"这个信号就拿不到，只能靠超时兜底弹 CTA，体验上不如自己的模板精确 |
| 适用场景 | 目标客户/广告方本身就是有真实 H5 试玩广告素材的游戏公司，希望"这条桥接内容用的就是我们自己真实的试玩广告"，而不是"AI 帮我们生成一个新的" |

## 三者的关系：不是非此即彼

方案 A 和方案 C 可以**同时存在**，按广告实际提供了什么来分流，不是互斥选择：

```
广告方提供了真实 H5 试玩包？
   ├─ 是 → 方案 C：直接拷贝，零生成
   └─ 否 → 广告类型命中已建好的模板？
              ├─ 是 → 方案 A：选中的模板 + LLM 填内容
              └─ 否 → 回退现在的翻牌配对模板（现状，不是退步，是兜底）
```

方案 B 现阶段不建议做，原因见上面——不是优先级问题，是风险量级和现有方法论不匹配的结构性问题，除非这个项目愿意为"验证动态生成的可执行代码"单独建一套新的、目前完全没有的安全/测试机制。

## 建议的优先级（如果要往下推进）

1. **先做方案 C**——工程成本最低（容器层地基已经在），如果业务侧确认能拿到真实 H5 试玩包，性价比最高，值得第一个做。
2. **再考虑方案 A**——只在业务上明确圈出 1-2 种高优先级玩法后再投入（比如已经有真实案例的三消），不要一次性铺开找不同/三消/拼豆一起做。
3. **不做方案 B**。

这份文档只是方案层面的对比，不是实现计划——真要动手的话，无论选 A 还是 C，都需要单独过一遍具体设计（输入方式怎么加、`ab_ad`/`ab_bridgeCut` 要不要加字段、`PlayableAgent.assemble()` 的分支细节、怎么验证），到时候再展开。
