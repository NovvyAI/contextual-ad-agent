PRODUCTION DESIGN DOC · AD-BRIDGE AGENT SYSTEM

广告桥接 Agent 架构设计

输入一集短剧 Episode 与若干广告素材，系统先构思全局创意方案供用户确认，再生成桥接内容，最终在 Episode 尾部拼接输出成片。本文档定义所需的全部 Agent、职责边界与端到端交互流程。

状态 设计评审稿 · Phase 1 日期 2026-07-22 受众 工程 / 产品 范围 仅 Episode 尾插，暂不支持片中任意位置插入

v0.4 相对 v0.3 的变化：原 DirectorAgent 的调度职责拆给新增的 SessionAgent，DirectorAgent 收窄为纯创意规划子 Agent，方案支持图片/视频/playable 的混合形式序列；明确「前端是确定性代码，LLM 只做自然语言理解」的分层原则。

01 — 概述

Phase 1 范围：只做 Episode 尾插

输入是一集短剧（几分钟或更短的 Episode）与若干广告素材（视频 / 图片 / 文字描述，任意组合）。插入位置由业务规则固定为 Episode 尾部，不做全片扫描与多候选位匹配。流程分两大阶段：批处理自动分析，随后进入对话式协作。

● 批处理阶段

自动分析

上传即触发，无需用户对话。产出 Episode 的结构化理解与每条广告的结构化画像。

↓
● 对话阶段

协作生成（两层）

先谈创意方案（文本，成本低），确认后才进入内容生成（媒体，成本高），两层都支持反馈重来。

为什么去掉了 PlacementAgent：插入位置已由业务规则固定在 Episode 尾部，不再需要一个 Agent 判断“插在哪”。这也让 StoryboardAgent 的产出从“全片逐镜带时间戳的分镜表”简化为“Episode 整体的结构化理解”——剧情、角色、情绪、画面、结尾状态，不再需要精细到镜头级别的切割定位。

03 — 分部门详解

每个 Agent 具体做什么

批处理部门 · 自动分析

2 个 Agent

StoryboardAgent adBridge:storyboardAgent

把一集 Episode 变成结构化的整体理解，不做逐镜时间戳切割。

输入
当前 Episode（视频文件 / S3 URL）
过程
全片抽帧 + 结尾密集抽帧 → 全片语音转写 → 多模态分析
输出
episodeAnalysis 剧情 / 角色 / 情绪基调 / 关键画面 / 结尾状态
协作
产出被 DirectorAgent、BridgeVideoAgent 读取

AdLibraryAgent adBridge:adLibraryAgent

把每条广告素材变成可用于创意构思的结构化画像，视频/图片/纯文字描述平级支持。

输入
广告视频 / 图片 / 文字描述，可组合，可多条并行处理
过程
视频类场景抽帧+转写；图片类直接读取；文字类直接结构化提炼
输出
ads[] 调性 / 商品 / 品牌安全标签 / hasVisualAsset
协作
产出被 DirectorAgent 用于构思创意方案

决策部门 · 会话调度

1 个 Agent

SessionAgent adBridge:sessionAgent

唯一的 Socket chat 入口，是「状态机 + 轻量 LLM」的结合体，不做创意构思，只负责调度和意图路由。

状态机
uploaded → plan_review → content_review → assembling，阶段流转本身是确定性代码，不经过 LLM
路由
用户的结构化操作（确认方案/选定内容）由确定性代码直接触发调度；只有自由文字反馈才交给内部 LLM 解析意图（比如判断这句话是针对哪个候选、该转给谁）
工具
run_sub_agent_director_plan_generate/_revise run_sub_agent_bridge_video_generate/_revise run_sub_agent_playable_generate/_revise run_sub_agent_overlay_generate/_revise run_supervision_agent get_workspace push_candidate
协作
是全部规划 / 执行 / 监督层 Agent 的唯一调用方

规划部门 · 创意方案

1 个 Agent

DirectorAgent adBridge:directorAgent

被 SessionAgent 当子 Agent 调用，专注创意构思，不做调度。产出可以是跨形式的混合脚本，不局限于单一形式。

输入
episodeAnalysis + ads[] + 用户对某份方案的反馈
过程
针对每条候选广告构思一份方案（文本，可能是「桥接视频 + playable」这类组合脚本，不是必须只选一种形式）→ 内部调用 PlanEvaluator 打分
输出
creativePlans[] 含 formatSequence[]（组合形式序列）+ 叙事构想 + 参考分
协作
产出交回 SessionAgent，由其推给用户、按确认结果调度执行 Agent

执行部门 · 内容生成

3 个 Agent，均含 generate / revise 双入口

BridgeVideoAgent adBridge:bridgeVideoAgent

生成单向桥接视频：从 Episode 结尾状态过渡到广告开场。内部分两阶段——先出便宜的图片分镜草案锁定细节，再渲染贵的成片。

输入
Episode 结尾参考片段 + 已确认方案 + 广告素材
过程
Stage A 生成分镜草案（图片，逐张 review）→ 全部确认后 Stage B 以这些 cut 作参考帧渲染成片
输出
bridgeCuts[] 分镜草案图 · bridgeCandidates[] 视频预览 + 六维参考分
展开 完整两阶段交互流程见 04 节「BridgeVideoAgent 内部展开」；尾插场景下取消了“广告 → 下一分镜”的回程桥接，只做单向。

PlayableAgent adBridge:playableAgent

把片头 + 互动小游戏 + CTA 装配成可玩广告包。

输入
已确认方案 + 广告素材（H5 包 / 品牌图标 / 文字）
输出
playableBundle 可预览的完整互动包

OverlayAgent adBridge:overlayAgent

生成片尾 CTA 卡片：商品图/文案 + 跳转按钮。

输入
已确认方案 + 广告商品信息
输出
ctaCard 静态卡片 + 跳转链接
待确认 目前理解是尾插场景下“内嵌链接”退化为片尾静态 CTA 卡片，而非片中悬浮热点。若产品仍需要叠加型热点形态，需重新确认，会影响下方 OverlayEvaluator 的评估维度。

监督部门 · 质量与合规

1 个 Agent

SupervisorAgent adBridge:supervisionAgent

落地前终审，范围比多插入位场景收窄——不再需要检查时间轴重叠或插入频率，因为全片只有一个固定插入位。

检查
内容合规、品牌安全、输出技术规格
不通过
打回 SessionAgent，指定环节需要重新生成或更换方案

工具调用部门 · 四个 Evaluator

均为内部调用，不暴露给 SessionAgent

非 LLM

04 — 用户交互流程与 Agent 调用

从上传到一键生成

对话阶段实际是两层独立的“候选 → 反馈 → 确认”循环：先在方案层用文字反复打磨（便宜），确认后才进入内容层做真正的媒体生成（贵）。

架构分层：前端（Vue3+TS，确定性组件渲染）↕ SessionAgent（状态机 + 轻量 LLM，只做意图路由）↕ 子 Agent 群（DirectorAgent / BridgeVideoAgent / PlayableAgent / OverlayAgent / SupervisorAgent，纯 LLM 创意与生成工作）。判断某个环节该不该用 LLM 的标准很简单：如果能写成 if/switch，就不用 LLM——按钮点击类的结构化操作（确认方案、选定内容）由确定性代码直接处理；只有自由文字反馈才需要 LLM 做意图解析。

为什么要分“贵”和“便宜”

“便宜”指生成快、算力低，改一次几乎不心疼；“贵”指生成慢、算力高，改一次要重新等待和付出算力成本。核心原则：越贵的阶段越不该用来试错——能在便宜阶段发现的问题（构图、表情、转场设想），都应该在便宜阶段解决掉；贵的阶段只用来验证“已经锁定的方案渲染出来对不对”，而不是用来“边生成边摸索创意”。这也是为什么整条链路是「文字方案 → 图片草案 → 视频成片」一层比一层贵。

05 — 关键交互模式

支撑上述流程的几个约定

成本分层迭代
不止方案层/内容层两层——BridgeVideoAgent 内部还要再插一层图片草案，把细粒度修改压到成本最低的阶段。原则和数据见 04 节。
两层候选循环
方案层（文本、便宜）与内容层（媒体、贵）是两个独立的“候选卡片 → 反馈 → 确认”循环，同一套交互模式在不同颗粒度上复用，但不能跳过方案层直接生成媒体内容。
generate / revise 双入口
每个执行 Agent 都提供两个入口而非一个通用「修改 Agent」：三种形式的修改方式完全不同，拆到各自 Agent 里更贴合实现。
Evaluator 按产出类型拆分
不用一个通用评分器套用所有内容——文本方案、视频、游戏、卡片的质量维度完全不同，各自的 Evaluator 只服务于对应的产出方。
Evaluator 只做预筛
所有评分都只是给用户看的参考信息，不做自动通过/拒绝，客观问题也只标警告，终审权全程留给用户。
单向参考驱动生成
桥接视频的连续性靠真实抽取的 Episode 结尾画面片段驱动生成，不是只靠文字 prompt 去猜测。

07 — 关键设计取舍

为什么这么设计

Phase 1 只做尾插，移除 PlacementAgent
插入位置由业务规则固定在 Episode 尾部，判断“插在哪”这件事不再存在，去掉相应 Agent 与全片分镜扫描能显著降低批处理成本和复杂度。
方案先行，执行后随
DirectorAgent 先用文字构思创意方案交给用户确认，SessionAgent 再据此调度真正的媒体生成，把试错成本压在便宜的文本迭代阶段，避免反复生成贵的视频/游戏内容。
桥接改为单向
尾插场景下广告后面没有视频需要接回去，双向桥接的“回程”部分不再有意义，直接砍掉降低生成成本。
Evaluator 一拆四，且统一只做预筛
不同产出类型（文本方案/视频/游戏/卡片）需要完全不同的评估维度，不能共用一套标准；同时无论维度是主观还是客观，都不做自动拦截，避免和用户判断冲突。
BridgeVideoAgent 内部再插一层图片草案
视频渲染是全流程里最贵的一步，不该承担“边生成边试错”的成本。插入一层便宜的图片分镜草案，把构图/表情/转场这类细粒度问题挡在便宜阶段，贵的阶段只做最终确认，减少整段重新渲染的次数。
SessionAgent 与 DirectorAgent 拆分
“会话调度”和“创意构思”是两种性质完全不同的工作——前者以确定性状态机为主、只在解析自由文字时才用到 LLM；后者是纯创造性任务。混在一个 Agent 里职责过重，拆开后 DirectorAgent 可以像其他执行 Agent 一样被 SessionAgent 统一当作子 Agent 工具调用，架构更一致。
创意方案支持混合形式序列，不再是单选一种形式
广告桥接不一定只用一种形式最合适——DirectorAgent 的方案现在可以指定多种形式的组合（比如桥接视频接一个 playable），更贴近真实创意需求，但也意味着 SessionAgent 的调度逻辑和 Assembler 的拼接逻辑都要能处理“一个插入位对应一段组合内容”。
前端是确定性代码，LLM 只做自然语言理解
LLM 输出不确定，不能负责决定何时展示什么 UI；候选卡片、分镜图、视频预览的渲染逻辑必须和内容生成解耦，否则没法维护。判断标准：能写成 if/switch 的（状态机流转、按钮点击路由、并发调度）都是确定性代码；只有解析自由文字反馈的意图才交给 LLM。这层协议直接扩展 Toonflow 现有的 ResTool 内容类型（content:add/content:update），新增 planCandidate/storyboardCut/videoCandidate/supervisorResult 几个 type，不另起一套事件系统。

待确认事项

?OverlayAgent 的最终形态——当前理解是片尾静态 CTA 卡片，而非片中悬浮热点。如果产品仍需要叠加型热点，OverlayEvaluator 的“遮挡情况”维度需要重新定义适用场景。
?是否要支持桥接到下一集开头——本版按“广告后无需接回视频”设计单向桥接；如果后续要做系列剧“追更”场景（广告后接下一集片头），BridgeVideoAgent 需要恢复双向能力。
?混合形式序列的执行顺序——一份方案指定「桥接视频 + playable」这类组合时，SessionAgent 派发对应执行 Agent 是并行生成、还是必须按序（比如先出视频再出 playable，因为后者可能要衔接前者的画面）？这个影响调度逻辑，需要确认。
