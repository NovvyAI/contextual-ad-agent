contextual-ad-agent · Agent 分步详解

每一步 Agent 做了什么：输入 / 输出 / 数据库交互

这份文档不是整体数据流向图（那份见 agent-data-flow.html），而是把管线拆成 10 个具体步骤， 逐步说明每一步用了哪个 Agent、读了什么系统提示（data/skills/*.md）和模型、输入输出的数据结构是什么、 以及具体读写了哪些 SQLite 表（src/lib/initDB.ts）。步骤顺序即用户从上传 Episode 到拿到最终交付物的真实操作顺序。

  1. 01Episode 分析
  2. 02广告素材分析
  3. 03创意方案生成 / 调整
  4. 04分镜草案生成 / 调整（Stage A）
  5. 05确认全部分镜草案
  6. 06成片渲染 / 运镜调整（Stage B）
  7. 07翻牌配对小游戏组装 / 调整
  8. 08自定义玩法生成 / 调整
  9. 09落地终审
  10. 10最终交付物组装
  11. 附录数据库表结构总览
Skill 文件

data/skills/*.md，运行时读入当 system prompt，决定 Agent 的判断标准和输出风格

数据库表

SQLite（ab_ 前缀），Agent 间真正的通信总线，大多只传 id、下游自己重新查库

Agent / 模型调用

实际执行 LLM 推理或图片/视频生成的调用节点

代码闸门 / 终审

不调模型、由代码或规则直接判定的检查点（如产物存在性检查、全部确认才推进）

01

Episode 分析storyboard_agent.md

StoryboardAgent.analyzeEpisode(episodeId)

把一整集短剧视频转成结构化的剧情/角色/情绪/结尾状态分析，是后面所有创意决策的地基。

输入

  • ab_episode.sourceFilePath（用户上传的短剧视频文件）
  • 代码预处理产出：fullFrames（全片按 2s 间隔抽帧）、tailFrames（结尾 10s 内按 1s 间隔密集抽帧）、台词转写（有音轨才做 ASR）

做了什么

把编号截图（Frame N / Tail frame N）+ 台词转写一起喂给 claude-opus-4-8，产出剧情梗概、主要角色列表、情绪基调随时间变化的节点、关键画面、结尾状态（含"观众看完后的情绪状态"这个供下游承接用的心理落点）。同时可选地从 fullFrames 里挑出最多 8 帧候选素材——优先保证每个主要角色都至少有一帧清晰展示外貌的画面。

代码再把候选帧序号映射成真实文件名（tileCandidates），不查模型。

输出

  • episodeAnalysisSchema 对象：plot / characters[] / emotionArc[] / keyVisuals[] / endingState{...} / tileCandidateFrameIndices[]

02

广告素材分析ad_library_agent.md

AdLibraryAgent.analyzeAd(adId)

和 Episode 分析并列独立进行，把上传的广告素材（视频/图片/文案）转成结构化的游戏信息和品牌安全判断。

输入

  • ab_ad 一行记录，按 adType 分三支：视频（sourceFilePath，按场景切换抽帧 + ASR）、图片（sourceFilePath 原图）、文案（textContent，截断 2000 字）

做了什么

claude-opus-4-8 分析素材的调性、游戏信息（名称/类型/核心玩法/视觉风格/卖点）、品牌安全（是否安全 + 风险点列表）、内容摘要；视频素材额外挑出最多 8 帧适合直接当配对小游戏素材的候选帧（要求画面清晰、能代表真实界面/玩法）。

输出

  • adAnalysisSchema 对象，代码补上 id/sourceType/hasVisualAsset/tileCandidates 组成完整 AdEntry

03

创意方案生成 / 调整director_creative.md + director_evaluator.md

DirectorAgent.generatePlans(episodeId, adIds) / revisePlan(planId, feedback)

两次独立模型调用：先构思方案，再单独打分评估——生成和评估的判断标准分别维护在两份 skill 里。

输入

  • ab_episode.episodeAnalysis（必须已分析完成）
  • 逐个 ab_ad（必须 status=analyzed），生成时可传多个 adId，通常一条广告对应一份方案
  • revise 额外输入：已有方案的 narrative/tone + 用户反馈文本

做了什么

① 生成阶段：针对每条候选广告构思承接 Episode 结尾的创意方案（narrative 叙事衔接 + tone 情绪基调）。② 评估阶段：对生成的每份方案打分（叙事衔接可行性 / 游戏关联度 / 广告匹配度 / 综合分 + 点评），返回数量必须和方案数一一对应，否则直接报错。

revise 是单条版本：只重新生成/评估这一份方案，不影响同批次的其他方案。

输出

  • 生成：每条候选广告一条新的 ab_creativePlan 记录（status=draft）
  • revise：原记录被覆盖更新（有损覆盖，不保留中间版本）

数据库交互

读 ab_episode, ab_ad, ab_creativePlan（revise）
写 ab_creativePlan（insert / update） 写 ab_reviseHistory（仅 revise，targetType=plan）

04

分镜草案生成 / 调整（Stage A）video_gen_agent.md

VideoGenAgent.generateDraftCut / reviseDraftCut(bridgeCutId, feedback)

先用文字模型定分镜设计，再拼装 prompt 用图片模型出草案图——两次调用，中间穿插一次自评分。

输入

  • ab_bridgeCut（type=video）→ loadPlanContext(creativePlanId) 反查 episodeAnalysis / ad / 已批准的 narrative+tone
  • 参考图（可选，各自缺失不影响主流程）：Episode 结尾最后一帧、广告代表帧（优先用 AdLibraryAgent 挑的 tileCandidates）、已组装完成的游戏真实素材帧（呼应用）
  • revise 额外输入：已有 scriptText + 用户反馈

做了什么

① 文字模型产出分镜设计：景别、运镜、主体动作/过渡呈现、光影氛围、情绪基调、构图备注、时长（6-15 秒自由决定，不固定值）；内部 evaluateDraft() 单独打一次参考分。② assembleStageAPrompt() 把参考图按 @图N 编号拼进最终 prompt，交给 resolveImageModelKey() 选出的图片模型（gpt-image-2 或 Gemini）生成草案图。

输出

  • 草案图文件（bridgeCut/{id}/draft-*.png）+ 组装后的完整 prompt

数据库交互

读 ab_bridgeCut, ab_creativePlan（imageModelKey）, ab_episode, ab_ad, ab_generatedSegment（游戏素材参考）
写 ab_generatedSegment（insert draftImage，旧版本 isSelected 清 0） 写 ab_bridgeCut（scriptText / prompt / status=draft） 写 ab_reviseHistory（仅 revise，targetType=bridgeCutDraft）

确认全部分镜草案无 skill · 纯代码闸门

VideoGenAgent.confirmAllCuts(creativePlanId)

不调用任何模型——用户点"确认全部分镜草案"时触发的确定性校验，全部满足才整体推进，不部分推进。

输入

  • 该 creativePlanId 下所有 type=video 的 ab_bridgeCut

做了什么

校验每一个 video cut 的 status 都是 draft，且都有一条已选定（isSelected=1）的草案图。任意一条不满足就整体报错拒绝，不会出现"一半确认一半没确认"的中间状态。

输出

  • 全部满足条件的 cut，status 统一置为 draftConfirmed——后续 Stage B 渲染的前置条件

数据库交互

06

成片渲染 / 运镜调整（Stage B）video_gen_agent.md（仅运镜 revise）

VideoGenAgent.renderStageB / reviseStageBMotion(bridgeCutId, feedback)

renderStageB 直接复用已确认的草案文案渲染，不再调文字模型；只有运镜专用 revise 才会重新问一次模型。

输入

  • 已确认的草案图（base64 + 公网 URL）+ 已确认的 scriptText
  • resolveVideoModelKey() / resolveVideoResolution() 读用户为该方案选定的视频模型（Seedance / Veo）和分辨率
  • 运镜 revise 额外输入：用户反馈——只允许模型改 cameraMovement / emotionalTone / durationS，其余字段强制锁定原值，避免 prompt 和已生成的静态图对不上

做了什么

assembleStageBPrompt(draft, videoModelKey) 拼装最终 prompt（Veo 会额外带一句"禁止出现文字"约束，Seedance 不加，见已知问题记录），以 singleImage 模式调用图生视频模型渲染成片。渲染完用 estimateActualDurationMs() 记录真实时长（Veo 是我们自己写死的规则，直接算得准；其他供应商用请求时的 durationS 近似），内部 evaluateRender() 再打一次参考分。

输出

  • 渲染视频文件（bridgeCut/{id}/render-*.mp4）

数据库交互

读 ab_bridgeCut, ab_generatedSegment（草案图）, ab_creativePlan（模型/分辨率选择）
写 ab_bridgeCut（status: rendering→done/failed，durationMs，运镜 revise 时也改 scriptText） 写 ab_generatedSegment（insert finalRender） 写 ab_reviseHistory（仅运镜 revise，targetType=bridgeCutMotion）

翻牌配对小游戏组装 / 调整playable_agent.md + playable_evaluator.md

PlayableAgent.assemblePlayable / revisePlayable(bridgeCutId, feedback)

默认路径（非自定义玩法）：生成配置 → 备素材 → 注入模板 → 收尾打包，四步都是同一个函数内顺序完成。

输入

  • ab_bridgeCut（type=playableGame）→ loadPlanContext()
  • 用户组装前可选勾选的候选参考图（Episode 帧或同方案 video cut 的草案图）
  • revise 额外输入：已有 PlayableConfig + 用户反馈

做了什么

① 生成游戏标题、CTA 跳转链接、2-6 条配对素材 prompt；内部 evaluatePlayable() 打分。② 备素材：优先用 ab_ad.tileCandidates（AdLibraryAgent 挑的真实游戏截图，≥2 张才用），否则按 tilePrompts 逐条用图片模型生成（可带参考图）。③ 注入 game.html 模板。④ finalizePlayablePackage()：把同方案 video cut 已渲染的成片复制为游戏包的片头 bridge.mp4，注入容器页 index.html，落库。

输出

  • 可交付的 playable bundle：index.html（容器）+ game/index.html（游戏本体）+ game/assets/tiles/*

数据库交互

读 ab_bridgeCut, ab_creativePlan, ab_ad（tileCandidates）, ab_generatedSegment（video cut 成片）
写 ab_generatedSegment（insert finalRender） 写 ab_bridgeCut（scriptText=config, status=done） 写 ab_reviseHistory（仅 revise，targetType=playable）

PlayableAgent.generateCustomGame / reviseCustomGame(bridgeCutId, description/feedback)

和默认翻牌配对路径完全独立：规格 → 素材 → 代码生成+真实浏览器冒烟测试的重试循环，失败兜底策略两条路径还不一样。

输入

  • 首次：用户的玩法描述（可长可短）；revise：已有 GameSpec + 用户反馈

做了什么

① 生成/调整 GameSpec：标题、CTA、玩法类型、通关目标、棋盘布局、交互规则、素材需求列表、"替用户做了哪些假设"列表——首次生成失败直接回退翻牌配对（步骤 07，保证总有产物交付）。② 按 assetsNeeded 逐条生成素材图。③ 代码生成 + 冒烟测试循环（最多 3 次：首次 + 2 次重试）：模型写游戏 HTML → Playwright 真实浏览器加载检测报错 → 不通过就把报错喂回重试。

失败兜底不对称：首次生成耗尽重试仍不过 → 回退翻牌配对；revise 耗尽重试仍不过 → 保留用户原有能跑的游戏不动，只报失败原因，不会用一个通用兜底顶掉用户本来满意的游戏。

附录：数据库表结构总览

存储是本地 SQLite（data/db2.sqlite），驱动是 better-sqlite3，通过 Knex 操作，表结构定义在 src/lib/initDB.ts（每次启动检查表是否存在，不存在才建，不做自动 migration）。 TypeScript 类型不是手写的——src/utils/db.ts 的 initKnexType() 每次 dev 模式启动时用 @rmp135/sql-ts 读当前库结构自动生成 src/types/database.d.ts， 所以新加一列之后，本地必须重启一次服务类型才会更新，改完代码类型报错先看是不是忘了重启。 下面先看这个项目实际业务用到的 8 张表（ab_ 前缀），再看数据库里还有哪些和业务无关、模板自带的框架表。

业务表（ab_ 前缀）

8 张表全部用 increments（AUTOINCREMENT）做主键，不是随手选的——这几张表都有删除功能，普通自增以外的主键删除后号码会被回收复用， 新记录可能撞上刚删掉的旧记录的 id，导致前端按 id 缓存的会话状态串号、显示已删除数据（真实踩过的坑，见 docs/CHANGELOG.md）。紫色标记的是外键列（references().inTable() 声明的引用关系，SQLite 默认不强制校验，纯靠约定）。

JSON blob 字段怎么存的

这是这套表结构最核心的设计取舍：结构化程度高、有下游要按字段查询/筛选需求的（id、状态、外键、时间戳）用真实列； 内容本身是"一整份复杂对象、只会被整份读出整份替换、不会按内部字段做 SQL 查询"的，直接 JSON.stringify 存进一个 text 列，读的时候 JSON.parse 回来。 这样每个 Agent 之间与其说是"共享数据库表结构"，不如说是"共享一个 id，下游拿着 id 查表、自己把 JSON 解析回对应的 TS 类型"——类型本身只在 Zod schema/TS interface 里定义，数据库层面完全不知道这些 JSON 里有什么字段。
