## 这个里程碑交付了什么

M7 把桥接流程定成了固定两段式管线，但 Agent 内部生成逻辑当时只求"能跑通"，`docs/milestones/M7.md` 明确记下了三处债：PlayableAgent 的配对小游戏素材完全是 AI 凭空生成的、VideoGenAgent 挑广告参考帧是纯机械的"取第一张"、SupervisorAgent 对 `playableGame` cut 的终审是纯文字的（从没看过任何一张实际画面）。M8 把这三处债一次性还清，核心思路是复用一个已有的免费信号：AdLibraryAgent 分析视频广告时本来就已经把最多 20 帧截图作为视觉输入喂给了 LLM，让同一次调用顺带指出"这些帧里哪些适合直接当配对小游戏素材"，这条判断同时喂给了 VideoGenAgent 的参考帧选择，不需要额外的 LLM 调用成本。

1. AdLibraryAgent 新增 `tileCandidates`——分析视频广告时，LLM 从已经看过的编号截图里挑出画面清晰、能代表游戏真实界面/玩法的帧，代码把选中的序号映射回实际帧文件名，存进 `analysisResult` JSON（不新建数据库列）；
2. PlayableAgent 组装配对小游戏时，优先直接拷贝这些真实截图作为配对素材，只有真实素材不存在或不够（少于 2 张）才回退到原来的 gpt-image-1 生成逻辑；
3. VideoGenAgent 选广告参考图时，优先用 `tileCandidates[0]`（已经验证过代表游戏画面的那一张），而不是机械地取文件名排序第一张；
4. SupervisorAgent 对 `playableGame` cut 的终审，这次真的会看一张实际画面（组装出的配对素材图），`codePreCheck` 也加了"游戏包/配对素材图是否存在"的检查，不再只看外层 `index.html` 存不存在。

## 关键设计取舍

1. **`tileCandidates` 不新建数据库列，直接放进 `analysisResult` JSON blob**——它和 `game`/`brandSafety` 一样，属于"广告分析结果整体读取复用"的数据，没有任何代码需要按它单独 `WHERE` 查询，不满足新建列的条件，遵循这个项目一贯的数据分类原则。
2. **候选帧的判断交给 LLM，不用机械规则**——`sampleFrames` 的 `scene` 模式只是 ffmpeg 场景切换检测，不保证抽到的帧都清晰、都是有效游戏画面（可能抽到黑场、转场）。这条选择本质是"这张截图好不好看、像不像真实游戏画面"，是视觉主观判断，符合这个项目一贯的分工原则——LLM 做质量判断，代码做确定性分支——而且这次判断直接复用了 AdLibraryAgent 分析视频广告时本来就在做的那次视觉调用，没有增加任何调用成本。
3. **PlayableAgent 真实素材门槛设成 ≥2 张**——呼应 `playableConfigSchema.tilePrompts` 自己 `.min(2)` 的门槛，只有 1 张真实截图时循环填充 8 格会让整个配对游戏所有卡牌都长一样，不如直接回退到 AI 生成、至少能保证素材多样性。
4. **`tilePrompts` 字段和它的生成逻辑保持不动，即使真实素材够用也不去改造"生成配置"的 LLM 调用**——不为了省一点点闲置的生成成本，给 prompt/schema 引入"是否有真实素材"这个条件分支，保持这次改动的范围小而聚焦。
5. **不改 `evaluatePlayable`**——它在时序上发生在真实/生成的图片产出之前，结构性地看不到图片；真正的把关在 SupervisorAgent 终审（这次已经升级能看图），`evaluatePlayable` 维持纯文本预筛不动。
6. **不引入无头浏览器截图**——用已经存在的静态 tile 图片做终审视觉输入已经够用，为了这一步引入 Playwright/Puppeteer 这类新依赖性价比太低。

## 遇到的问题与处理

1. **`u.Ai.Image(...).run()` 的结果字段是私有的，不能直接从外部脚本读取**——写生成测试素材的脚本时第一次尝试直接访问 `image.result` 拿 base64，`tsx` 运行时不做严格类型检查所以能跑，但这是绕过封装的错误用法。改成用类已经暴露的 `.save(relPath)` 写入 OSS，再用 `u.oss.getFile(relPath)` 读回 Buffer，和项目里所有其他调用点保持一致的用法。
2. **一次真实调用命中了图片供应商的临时超时**（"origin web server did not return a complete response within the 120-second Proxy Read Timeout"）——和这次改动无关的上游网络抖动，`cut.status` 正确落到 `failed`，直接重跑一次 `generateDraftCut` 后续流程全部走通，不是代码 bug。
3. **`buildSupervisionMessages` 的图片 `mediaType` 一直写死 `"image/png"`**——此前唯一会附图的场景（video 类型的 Stage A 草案图）确实都是 png，这个问题从来没被暴露过；这次新增的 playableGame 配对素材图（真实截图是 `.jpg`）第一次真实触发了这条路径，顺手按扩展名修正。

## 已知限制（不在这次范围内）

- **`evaluatePlayable`（组装前的预筛评分）依然是纯文本，看不到图片**——结构性限制，见上面"关键设计取舍"第 5 条，真正的把关在终审这一步。
- **没有引入无头浏览器截图验证组装出的 `game.html` 实际渲染效果**——现在的视觉输入是"用了哪张配对素材图"，不是"游戏界面渲染出来长什么样"，这是更进一步、成本也更高的验证手段，留给以后有需要再考虑。
- **老数据不会回填 `tileCandidates`**——M8 之前分析过的广告不会重新跑分析去补这个字段，所有消费点都按"可能是 undefined"处理，不强制升级历史数据。
- **前端**——按 M7 定的节奏留给 M9，这次没有改动任何前端代码。
