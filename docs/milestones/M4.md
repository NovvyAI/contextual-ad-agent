## 这个里程碑交付了什么

M3 把三种桥接形式的生成/revise 都做通了，但状态机在 `content_review` 就断了——没有代码把 `workflowStage` 推进到 `assembling`。M4 补上这最后一段：

- **SupervisorAgent**：落地前终审，**真正的拦截关卡**，和 M2/M3 那四个"只做预筛、终审权留给用户"的 Evaluator 不是一回事——不通过就打回，不是标个警告了事。先做代码层面的产物存在性检查（客观可判断，不浪费模型调用），通过了再调用 Claude 做"内容合规/品牌安全/技术规格"三维实质审核。
- **Assembler**：纯代码，无 LLM。按内容形式三分支组装最终交付物——`video` 真实 ffmpeg 拼接 Episode 原片+桥接视频，`playableGame` 直接复用 M3 已经自包含的游戏包，`ctaCard` 把 Episode 原片复制进可访问的存储位置、CTA 卡片作为附加资产登记。写一行 `ab_manifest`。

这是原始里程碑规划（M0-M4）的最后一环——走到这里，从"上传 Episode+广告"到"落地成一个真实可访问的最终交付物"的完整链路全部打通。

## 这次规划前的一个前置决定

规划 M4 之前，这次会话里先做了一个范围收窄：**`ab_creativePlan.formatSequence` 现在永远只有一个元素**（DirectorAgent 的字段从数组 `formatSequence` 改成单值枚举 `format`，详见 `docs/milestones/M2.md` 补记）。这意味着每份已批准方案永远只对应一个 `ab_bridgeCut`，M4 完全不用处理"一个插入位是组合形式"的拼接逻辑，架构文档自己标的"待确认"问题（混合形式执行顺序）随之消失。

## 关键设计取舍

1. **SupervisorAgent 是真正的拦截关卡，不是第五个 Evaluator**——架构文档把"只做预筛、终审权留给用户"这条统一原则明确限定在"四个 Evaluator"身上，SupervisorAgent 单独属于"监督部门"，措辞是"打回"不是"参考分"。
2. **状态转移设计成"守卫和变更分离"**，见上表 `state.ts` 的说明——不需要为失败场景写任何"回退"代码，M3 已经建好的 revise 工具直接就是用户下一步能做的事。
3. **SupervisorAgent 不需要 skill 文件**——这是对 work-plan 原话（"SupervisorAgent 落地前终审 + skill 文件"）的一次偏离，理由和 M2 处理 DirectorAgent 时一样：M1-M3 实际约定是每个 Evaluator/Agent 的 system prompt 是 `prompt.ts` 里的内联常量，`data/skills/` 目前只有一个文件（给 SessionAgent 做意图路由用），不是给 Evaluator 类角色用的。
4. **判定顺序：先代码检查，再 LLM**——产物文件/目录不存在这种客观问题，不该花一次模型调用。
5. **`invokeObject` 而不是文档表格里写的 `.invoke()`**——文档的模型映射表是早期写的，那时候 `invokeObject` 这个结构化输出约定还没建立，M1-M3 所有 Evaluator 都用 `invokeObject`，SupervisorAgent 作为真拦截关卡更需要结构化输出。
6. **`runSupervision`/`assemble` 都拆成"按 cut 直接操作"+"按方案走正式不变量校验"两层**——和 `bridgeVideoAgent`/`playableAgent` 那套"核心函数 vs 正式入口"的分层是同一个思路，方便直接对 legacy 多 cut 测试数据（范围收窄之前留下的）做验证，不用为了测试专门造新数据。

## 遇到的问题与处理

1. **Smoketest 一开始硬编码了"必须 passed:true"的预期**——`contentConfirmSocket.ts` 最初的"通过路径"断言直接要求终审结果 `passed===true`，结果真实调用时 LLM 诚实地判定我们的合成测试素材（SMPTE 彩条测试图+占位链接）不算真正可交付的内容，`passed:false`——这其实是终审机制在正确工作，不是 bug。改成不硬编码预期结果，转而断言"无论结果是什么，后续编排都和这个结果保持一致"（通过则走 Assembler，未通过则确认没有误触发）。为了确保"通过之后的编排"这条路径本身也被验证到（不能只靠一个真实但不可控的 LLM 判断），额外加了一段直接用构造好的 `passed:true` 结果调用 `assemble()+enterAssembling()` 的验证，绕开 LLM 判断的不确定性，专门测这段确定性代码编排本身是对的。
2. **SessionAgent 的 system message 警告一直没修**——见上表，这次顺手修了。
3. **一次"看起来像卡住"的假警报**——`contentConfirmSocket.ts` 里验证"拦截后 chat revise 仍然可用"这一步，两次都在等待超时（先 180s 后 300s）里失败，一开始怀疑是网络/中转站卡住。用一个最小化的诊断脚本（连 socket、发 chat、把所有事件原样打印出来）才发现真相：测试消息"请把分镜草案 id=X 重画一下"太含糊，LLM 正确地识别出这条反馈没说清楚要改什么，没有调用 revise 工具，而是反问用户想要什么样的调整——这是 SessionAgent 的意图路由在正确工作，不是 bug。把测试消息改成带具体修改意见（"画面再明亮一点"，和 M3 `bridgeCutSocket.ts` 里已经验证过的措辞一致）就解决了。

## 已知限制

- 由于测试素材本身是合成的 SMPTE 技术测试图案（不是真实短剧内容），`content:confirm` 的"真实内容终审通过"这条分支从未在端到端 socket 测试里被一个真实、诚实的 LLM 判定为 `passed:true` 过——这条分支的编排正确性是通过直接构造 `passed:true` 结果单独验证的（见上），但"LLM 对真正合格内容给出通过判定"这件事本身，要等接入真实短剧素材才能观察到。
- SupervisorAgent 复用 Stage A 的草案图（而非 Stage B 渲染成片的真实帧）作为 `video` 类型的审核依据，理由是效率（不为了终审重新抽帧），但严格来说草案图和最终渲染成片可能有细微出入，如果以后发现这个差异重要，需要改成从渲染成片重新抽帧。
