## 关键设计取舍

1. **revise 失败时的兜底和首次生成不一样**——首次生成失败要回退翻牌配对（保证有东西交付）；`reviseCustomGame` 失败时保留用户已有的、能跑的自定义游戏不动，不能用一个通用的翻牌配对顶掉用户本来满意、只是想小改的游戏。这条区分从一开始设计 revise 时就明确写进了函数注释里。
2. **候选素材的选择完全交给用户，系统不自动选或忽略**——和这个项目一贯"确定性的选择交给用户，不该由 LLM/代码隐式决定"的原则一致；不选也能正常生成（保持默认路径体验不变），不做成强制/阻塞步骤。
3. **选中的候选帧不直接复制使用**——M8 已经踩过这个坑（原始截图硬塞进结构化素材槽位，风格和构图对不上），这次统一走 `u.Ai.Image(...).run({ referenceList })` 参考图机制，生成风格匹配游戏、但保留真实角色/场景样貌的干净素材。专门做了一次隔离测试验证 gpt-image-1 的 `referenceList` 真的会保留人物发型/配饰等细节，不是摆设。
4. **Episode 抽帧候选素材新增独立的 `/episode` 静态路由，不复用 `/oss`**——`data/episode/` 是分析阶段的中间产物目录，和 `/oss` 承载的最终交付物是不同性质的数据，参照 `/skills` 的先例单独开一个只允许图片扩展名的静态路由，不把两类目录混在一起。
5. **游戏素材参考图按"自定义生成 vs 默认翻牌配对"区分文件名**——两条路径素材落盘的相对路径不同（`custom_0.png` vs `tiles/tile_src_0.jpg`），复用了别处已有的"`scriptText` 能否解析出 `gameType` 字段"判断依据，不新增额外的标记字段。
6. **视频呼应游戏素材不做自动触发**——用户主动发起 revise 才会带上这个参考图，不引入"游戏组装完自动重新生成视频"这类新的自动化判断逻辑，符合计划里"明确不做的"约定。

## 遇到的问题与处理

1. **`ActionBar.vue` 里两个新增的 `<t-dialog>` 插在了 `v-if`/`v-else-if` 链的中间**——Vue 编译报错 "Codegen node is missing for element/if/for node"，浏览器打开页面直接白屏。这不是逻辑错误而是模板结构错误：`v-else-if` 必须紧跟在前一个 `v-if`/`v-else-if` 兄弟节点后面，中间不能插别的元素（哪怕之前只插了一个 `t-dialog` 也已经是隐患，这次新增第二个才真正触发编译失败）。修复方式是把两个 `t-dialog` 都挪到整条 `v-if` 链结束之后，作为平级兄弟节点。这是一个通过真实浏览器走查才发现的 bug，再次印证了这个项目"必须真实验证渲染效果，不能只看类型检查"的一贯做法——`vue-tsc` 对这类模板结构错误完全没有检测能力。
2. **测试用的 `m8-test-game-ad` 广告自带 ≥2 张真实 `tileCandidates`**——按 M8 的逻辑，`assemble()` 会直接复用这些真实截图，走不到这次新加的 AI 生成兜底分支（也就是候选素材 `referenceList` 真正生效的分支）。发现后改用自定义游戏生成路径（`acquireCustomGameAssets` 永远走 `u.Ai.Image`，没有直接复用分支）单独验证参考图线程，确认技术上确实生效。
3. **反复出现的供应商侧临时不可用**（"Upstream request failed"）——这次验证过程中出现了两次，都是在图片生成调用上，重试后即恢复，日志确认代码走到了预期的分支和行号，判定是外部依赖抖动，不是代码 bug（和 M8 验证时的经验一致）。

## 已知限制（不在这次范围内）

- **自定义游戏素材的"只重生成变化槽位"精细优化不做**——`reviseCustomGame` 每次调整都整批重新生成素材，和 `reviseDraftCut` 每次整张重画草案图是同一个简单化取舍。
- **视频呼应游戏素材不做自动触发**——只在用户主动发起视频 revise 时才会带上游戏素材参考图，不引入"游戏组装完自动重新生成视频"的自动化逻辑。
- **老数据不会回填 `tileCandidates`**——M9 之前分析过的 Episode 不会重新跑分析去补这个字段，所有消费点都按"可能是 undefined"处理。
- **Episode 候选素材缩略图目前只服务于生成游戏素材这一个场景**——静态路由本身是通用的，但没有在其他地方（比如 Episode 列表页）复用展示。
