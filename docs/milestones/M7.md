## 这个里程碑交付了什么

M0-M6 建立的架构里，DirectorAgent 每份创意方案要在三种桥接形式（video / playableGame / ctaCard）里三选一，一份方案对应一个 `ab_bridgeCut`。业务方向变了：广告素材固定是"游戏视频"或"游戏文字"，桥接体验也固定成一套流程——AI 生成一段过渡视频，从 Episode 结尾承接到"游戏开始"这个时间点，紧接着是一个真实反映该游戏的 H5 配对小游戏。M7 把这条固定两段式管线的骨架搭起来：

1. StoryboardAgent 的 Episode 分析新增 `viewerEmotionalState`（观众看完后的情绪状态，区别于剧中情绪的 `emotionArc`），供桥接内容设计心理落点参考；
2. AdLibraryAgent 的产品视角字段 `product` 整体改成游戏视角的 `game`（新增 `genre`/`coreMechanic`/`visualStyle`）；
3. DirectorAgent 不再选形式——删掉 `formatTypeSchema`/`format`/`formatFit`，新增 `gameRelevance` 评分维度，`ab_creativePlan.formatSequence` 列连带删除；
4. `ab_bridgeCut` 硬编码固定两段（`video` → `playableGame`），OverlayAgent 和 ctaCard 概念整体删除（不留兼容壳子）；
5. PlayableAgent 组装游戏包时，`bridge.mp4` 从"读 Episode 尾帧占位"改成"读同一方案下 video 段真实渲染出的成片"；
6. 新增一个手动确认点——video 段成片渲染完不会自动直通组装小游戏，需要用户在界面上点击"确认组装小游戏"才触发（新 socket 事件 `bridgeCut:assemblePlayable`）。

## 交互流程（这次确认下来的最终版本）

```
1. 点「生成创意方案」→ DirectorAgent 只挑广告、写 narrative/tone，不再选形式
2. 点「确认该份方案」
3. 点「生成内容」→ 自动生成桥接视频的 Stage A 草案图（只生成 video 段，playableGame 段先建行但不动）
4. 点「确认分镜草案，开始渲染成片」→ 自动渲染 Stage B 成片
5. （成片渲染完，停下来——新增的手动确认点）
6. 点「确认组装小游戏」→ 把成片嵌进小游戏包、生成配对素材
7. 点「确认内容，进入终审与落地」→ SupervisorAgent 终审（只审 playableGame 段）+ Assembler 落地
```

## 关键设计取舍

1. **一份方案永远两个 cut，不再有可变数量的 `formatSequence`**——`createBridgeCuts` 直接硬编码 `["video","playableGame"]`，`assertContentReady`/`runSupervision`/`assembler.assemble` 统一改成"从两个 cut 里挑出 `playableGame` 那个"，因为它是唯一真正的最终交付物，video 段的产物已经被内嵌进它里面，不再单独走终审/落地。
2. **手动确认组装小游戏，不自动直通**——这是这次设计讨论里明确定的用户体验：video 成片渲染完之后停下来，让用户先看到过渡视频的效果，主动点击才继续生成小游戏，而不是无感知地自动往下跑。为此新增了 `bridgeCut:assemblePlayable` 这个独立的 socket 事件，而不是把两步做的事塞进 `bridgeCut:confirm` 里。
3. **ctaCard/OverlayAgent 直接删除，不保留兼容壳子**——这是用户在讨论新流程时明确选择的"直接替代，以后只有这一种流程"，也符合项目一贯的约定（确定不用的东西直接删，真要恢复 git 历史里找得回来）。受影响的旧 smoketest（`bridgeCutSocket.ts`/`contentConfirmSocket.ts`）一并替换成新写的 `m7BridgeFlow.ts`，而不是打 TODO 补丁勉强让它们编译过。
4. **PlayableAgent 的 `bridge.mp4` 来源换成真实视频，这一步没有推迟到 M8**——虽然计划里"游戏内部生成逻辑的精修"整体划给了 M8，但"游戏包里嵌的到底是不是真实过渡视频"这件事直接决定 M7 能不能算真正跑通两段式（而不是挂着假数据的空壳），所以提前在 M7 做了。做法很直接：`assemble()` 多传一个 `creativePlanId`，查同一方案下 `type="video"` 的 cut 的 `finalRender` 产物，`u.oss.getFile()` 读出来直接写进 `bridge.mp4`。
5. **`viewerEmotionalState` 是纯新增字段，不影响任何现有消费方**——加在 `endingState` 下面，`storyboardAgent/prompt.ts` 补一句要求模型把"观众情绪"和 `emotionArc` 描述的"剧中情绪"分开分析，避免模型把两者答混。

## 遇到的问题与处理

1. **旧数据（M1-M6 时期分析过的 Episode/广告）在新 schema 下会直接崩掉**——`directorAgent` smoketest 第一次跑的时候，`episode.episodeAnalysis`（M1 时期分析的、没有 `viewerEmotionalState`）和 3 条广告的 `analysisResult`（没有 `game` 字段，只有旧的 `product`）都触发了 `Cannot read properties of undefined` 崩溃。这不是 bug，是预期之中的"给已有 JSON blob 加字段"的真实迁移问题——处理方式是直接对 episode 1 和广告 1/2/3 重新跑一遍 `analyzeEpisode`/`analyzeAd`，而不是在 prompt 拼装代码里加可选链兜底旧数据（项目约定：不为不会再出现的旧数据形状写兼容代码，直接让数据源头刷新）。
2. **`scripts/smoketest/m7BridgeFlow.ts` 第一次跑超时**——初版 `TIMEOUT_MS` 定的 300s，真实链路（登录→方案生成→确认→分镜草案→Stage B 视频渲染→小游戏组装，其中小游戏配对素材是 2-6 张图顺序调用 `gpt-image-1`，单张接近 1 分钟）跑到"组装小游戏"这一步在 300s 超时。这不是逻辑 bug——服务端的生成任务本身在客户端脚本超时退出后依然继续跑完了（`playableAgent.assemble()` 是纯服务端异步流程，不依赖发起请求的客户端存活），事后用同一个 episode/plan 手动补发了一次 `content:confirm` 确认了完整链路，随后把 `TIMEOUT_MS` 提到 600s，避免以后重跑再出现这个误报。

## 已知限制（明确留给 M8）

- **PlayableAgent 内部生成逻辑还是旧的 AI 生成配对图**——`assemblePlayable` 目前只是把 `bridge.mp4` 换成了真实视频，配对素材（`tilePrompts`）仍然是 LLM 凭空构思、AI 生成的抽象图片，不是真实截取自广告游戏视频的实机截图。真实截图提取（`AdLibraryAgent` 存 `tileCandidates`、`sampleFrames()` 抽帧管线）是 M8 的事。
- **VideoGenAgent 的 prompt 还是松散的 `{prompt, framingNotes}` 两个字段**——M8 计划参考 Toonflow-app 的结构化视频 prompt 模板（`@图N` 编号引用、标准化景别/运镜词汇表）重写，这次只做了 `.product`→`.game` 的字段改名，没有动生成逻辑本身。
- **SupervisorAgent 对 playableGame 的终审还是纯配置审核**——这次真实验证观察到的 `technicalSpec: 20` 分低分，本质原因也是"没有真实游戏截图/可运行产物"，等 M8 接上真实素材管线之后，终审的判断质量会同步提升，不需要现在改终审逻辑本身。
- **前端 UI 没有做针对新流程的精修**——`ContentCandidateCard.vue`/`ManifestCard.vue` 仍保留着未被使用到的 ctaCard 展示分支（不影响编译和运行，只是死代码），`PlanCandidateCard.vue` 的"形式"这一行目前是写死的静态文案。这些留给 M9 前端里程碑一起处理。
