## 这个里程碑交付了什么

M2 把"确认一份创意方案"做通了，但方案里 `formatSequence`（如 `["video","ctaCard"]`）指定的内容一个都没真正生成。M3 补上这一层——三个执行 Agent，各自能生成候选、接受局部反馈重新生成：

- **BridgeVideoAgent**：唯一需要两阶段的执行 Agent。Stage A 出便宜的图片分镜草案（逐张 review，"只重画这一张不影响其他"），全部确认后 Stage B 用确认的草案图当参考帧渲染成片（真实调用 Seedance）。
- **PlayableAgent**：纯装配，不是 LLM 生成游戏——照 Python 参考实现 `build_playable.py` 移植的 ffmpeg 拼接 + 模板注入逻辑，配对小游戏的素材图由 `u.Ai.Image` 生成。
- **OverlayAgent**：最简单，单阶段生成静态 CTA 卡片（产品图 + 文案 + 跳转链接）。

三者共用同一套 Evaluator 原则（预筛、参考分、终审权留给用户），由 SessionAgent 并行派发，工作边界到"用户确认内容"为止——`assembling` 阶段的 ffmpeg 拼接/manifest/SupervisorAgent 终审是 M4 的事，这次不碰。

## 几个关键设计取舍

1. **`ab_bridgeCut` 是三个形式共用的一张表**——一份方案的 `formatSequence` 里每个位置对应一行（`index`+`type`），由 `state.createBridgeCuts()` 统一建行，再按 `type` 分发给对应 Agent，三个 Agent 都不自己建行，避免各自重复"我是方案里第几个位置"的判断逻辑。
2. **`isSelected`/`stage` 是三个 Agent 通用机制**，不是 BridgeVideoAgent 专属——虽然 Playable/Overlay 没有"阶段"概念，但复用同一套字段让"查当前生效产物"的查询方式在三个 Agent 之间保持一致（`where bridgeCutId=? and stage='finalRender' and isSelected=1`），比只给 BridgeVideoAgent 单独加字段更简单。
3. **PlayableAgent 不生成游戏本身，只做装配**——已完整读过 `ads-gen-agent-main/build_playable.py`（287 行）验证：核心是 ffmpeg 拼接 + 静态资源拷贝 + 一个正则占位符替换（把 JSON 塞进 `<script>`，不是真正的模板引擎）。TS 版本原样移植了这套逻辑，只有配对素材图片和标题/CTA文案是新增的 LLM+图片生成步骤（Python 参考实现要求人工传入素材，我们这边自动生成）。
4. **OverlayAgent 不生成 HTML**——CTA 卡片和 Playable 不一样，不是要交付给最终用户的可运行制品，是要展示在前端 UI 里的一张卡片，所以只产出结构化数据（`ab_bridgeCut.scriptText` 存 JSON）+ 一张产品图，不新写 HTML 模板。
5. **三个新 Evaluator 都不做自动循环**——Python 参考实现的 `evaluator.py` 是自动"生成→评估→revise"循环（`max_iterations`），这次没有照搬：BridgeVideoEvaluator（六维）、PlayableEvaluator（两维）、OverlayEvaluator（三维）都只是预筛打分，跟着候选内容一起推给用户，终审权在用户，和 M2 的 PlanEvaluator 是同一个模式。
6. **混合形式并行派发**——架构文档把这个列为待确认问题，这次决定并行：`bridgeCut:generate` 一次性对所有格式发起生成，各自独立跑 generate/revise 循环，BridgeVideoAgent 自己的两阶段流程是它内部的事，不影响这个决定。
7. **"全部草稿确认"是按钮操作，不是 LLM 工具**——新增 `bridgeCut:confirm` socket 事件，和 `plan:approve` 是同一个写法，延续"结构化操作用确定性代码"的原则。

## 遇到的问题与处理

1. **`data/vendor/openai.ts` 是占位实现**——和 M0 写 `anthropic.ts` 一样的情况：Toonflow 抄过来的模板里 `imageRequest`/`videoRequest`/`ttsRequest` 都是空字符串占位，`models` 里也没有图片模型。这次把 `imageRequest` 写成了真的（`/images/generations` 纯文本，`/images/edits` 带参考图），顺便发现并修正了这个文件里 `ImageConfig`/`VideoConfig` 本地类型声明还停留在旧版本的 `imageBase64: string[]` 字段（和 `grsai.ts` 已经用的 `referenceList` 约定不一致），一并改成当前约定。
2. **参考图 base64 前缀的坑**——`ab_generatedSegment` 里存的图片是通过 `u.oss.writeFile`/`getFile` 管理的，读回来是纯 base64（无 `data:` 前缀）；但不同供应商脚本对 `referenceList[].base64` 的前缀假设不一致（`imarouter.ts` 会自己拼 `data:image/png;base64,` 前缀，如果传入的值已经带前缀会导致双重拼接）。最终统一约定：Agent 层构造 `referenceList` 时一律传**不带前缀的原始 base64**，这样 `imarouter.ts` 自己拼前缀能正确工作，`openai.ts` 那边也做了防御性的前缀剥离（正则匹配到就去掉，没匹配到就保持原样），两边都不会出错。
3. **OpenAI 官方 key 直接被拒（401 Incorrect API key）**——不是代码问题，key 本身有效性有问题，让用户自己去 OpenAI 后台确认；后来用户换成中转站的 key。
4. **中转站分组不支持图片生成**——中转站返回 `分组 openai-embbding 下模型 gpt-image-1 无可用渠道`，说明这个 key 当时被分到的分组只开通了 embedding 能力。用户在中转站那边重新选组后，`gpt-image-1` 的文生图和图生图都跑通了。这两步都是用户账号/中转站配置问题，没有改任何代码。
5. **测试数据里 episode 没有真实 tail.mp4**——`playableAgent.ts` smoketest 用的 episode（M2 smoketest 克隆出来的）只克隆了 DB 字段，没有克隆实际的 `tail.mp4` 文件，所以 `assemblePlayable` 里 `has_video` 正确判断为 `false`，装配流程优雅跳过了视频拼接分支——这是测试数据本身的限制，不是代码 bug，`assemblePlayable` 对"没有视频"这个分支的处理是正确的。

## 已知限制 / 留给后续里程碑

- `concatVideos()` 已实现但 M3 baseline 流程没有实际调用路径触发过（PlayableAgent 目前只用单段 tail clip 直接复制）——留给以后需要真正拼接桥接视频时验证。
- PlayableAgent 目前不支持"外部 H5 包"模式（Python 参考实现的 `--game-dir` 分支），只实现了内置配对游戏模板这一种；如果后续需要广告主提供现成 H5 包，这块要补。
- BridgeVideoAgent Stage B 目前固定 6 秒时长、单参考图模式，没有实现 Python 参考实现里"超过 15 秒自动分段串联"的逻辑——当前项目场景（片尾单向桥接）暂时不需要长视频。
- OverlayEvaluator 的"遮挡情况"维度对纯静态片尾卡片场景意义不大（架构文档本身也在 `schema.ts` 里标注了这一点），如果以后真的要支持片中悬浮热点，这个维度才会真正派上用场。
